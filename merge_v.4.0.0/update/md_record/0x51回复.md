# 0x51 复位回复缺失问题说明

> 主题：UDS 刷写完成后，TBOX 发 `0x11 ECUReset`，ECU 应跳回 APP 后补发 `0x51` 确认复位完成；第一次烧录时总线上一直没有 `0x51`，导致 TBOX 超时重试。
> 涉及工程：`D:\ota_ddl3.3_v.3.1\merge_v.2.0.0\boot`（bootloader）、`D:\260706_NL`（四驱 APP1/APP2）。

---

## 1. 现象（CAN 记录 123123.trc）

第一次刷写 APP1 完整走完后，TBOX 发送 `0x11 01`（ECUReset），但总线上**没有出现 `0x51` 肯定响应**：

| 消息号 | 时间(ms) | 方向 | ID | 数据 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 11637 | 48917.4 | Rx | 18DA03F1 | `02 11 01` | TBOX 发 ECU 复位 |
| （无） | 48917.4 ~ 54922.7 | — | — | — | **约 6 秒无任何响应** |
| 11644 | 54922.7 | Rx | 18DA03F1 | `02 10 02` | TBOX 超时后重新建立会话 |

而第三次烧录完成后，同样的 `0x11 01` 却有 `0x51`：

| 消息号 | 时间(ms) | 方向 | ID | 数据 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 23316 | 95245.7 | Rx | 18DA03F1 | `02 11 01` | TBOX 发 ECU 复位 |
| 23317 | 95655.6 | Rx | 18DAF103 | `04 51 01 00 00 00 00 00` | **APP 复位后补发 0x51**（+410ms） |

`04 51 01 00 00 00 00 00` 解析：ISO-TP 单帧长度 4 → `51`(ECUReset 肯定响应) `01`(hardReset) `00 00`(填充)。

---

## 2. 预期设计（为什么 51 应该由 APP 补发）

- 刷写完成后 boot 收到 `0x11`，**不在复位前直接回 `0x51`**；
- boot 把 `pending_sid=0x11` 写入 UDS 共享区（flash），延迟约 100ms 复位；
- boot 复位后按自动跳转槽跳回 APP；
- **APP 启动时** `App_CheckPendingUdsAck()` 读到 `pending_sid=0x11`，补发 `04 51 01 ...`，告诉 TBOX“已经复位完成”。

即：`0x51` 是 APP 启动后的“补发确认”，不是 boot 复位前的即时响应。

---

## 3. 补发链路（触发条件）

整条链路要成功，必须**同时**满足：

1. boot 收到 `0x11`（`SCB->VTOR==0`，bootloader 上下文）时，`UDS_SHARED.magic == UDS_SHARED_MAGIC`，才写入 `pending_sid=0x11`；否则打印 `WARNING: magic mismatch` 且**不写**；
2. 复位后 APP 启动 `App_CheckPendingUdsAck()` 时，`UDS_SHARED.magic == UDS_SHARED_MAGIC`，否则 `if (s.magic != UDS_SHARED_MAGIC) return;` **直接返回**；
3. `pending_sid == 0x11`，才发送 `04 51 01 00 00 00 00 00`；
4. 补发完成后 `UdsShared_Clear()` 清共享区。

相关代码：
- boot：`Bootloader_App.c`（`Bootloader_UdsMain`）、`UDS\uds_diagnostic.c`（0x11 处理）
- APP：`D:\260706_NL\project\app1|app2\app\can\uds\bootloader_app.c`（`App_CheckPendingUdsAck`）

---

## 4. 根因

`Bootloader_UdsMain()` 烧录完成写 UDS_SHARED 时，**没有强制 `state.magic = UDS_SHARED_MAGIC`**，而是“读旧值 → 改 phase/result/target_slot → 写回”，magic 沿用了旧值：

```c
UdsShared_Read(&state);              // state.magic = 旧记录（可能是 0xFFFFFFFF）
state.phase = UDS_PHASE_PROGRAMMING_DONE;
state.result = 1;
state.target_slot = eSlot;
UdsShared_Write(&state);             // ← magic 仍是旧值！
```

对比其它写 UDS_SHARED 的地方（都显式写了 magic）：

```c
// UdsShared_SetPhase()（boot / APP）
state.magic = UDS_SHARED_MAGIC;      // ✓

// APP 0x31 进 bootloader 例程
_st.magic = UDS_SHARED_MAGIC;        // ✓
```

### 为什么第一次失败、第三次成功

- **第一次**：ECU 是“双坏等待 UDS”进 boot（该入口不写 UDS_SHARED），且 APP 上次启动时已 `UdsShared_Clear()` 把共享区擦成 `0xFFFFFFFF` → 烧录完成写回时 `magic=0xFFFFFFFF`（无效）→ `0x11` 时条件 1 不成立（不写 pending_sid）→ APP 启动时条件 2 不成立（直接 return）→ **总线上没有 0x51**。
- **第三次**：第二次会话中 APP 的 `0x31 FE00` 例程写入了有效记录（`magic=UDS_SHARED_MAGIC`）→ 第三次烧录完成读到有效 magic 并保留 → `0x11` 写 pending_sid 成功 → APP 启动补发 `0x51` ✅。

---

## 5. 解决方案与步骤

### 改动（1 个文件）

`merge_v.2.0.0\boot\projects\ev_hc32f460_lqfp100_v2\Bootloader_App\Bootloader_App.c` → `Bootloader_UdsMain()`，在 `UdsShared_Write(&state)` 前强制写 magic：

```c
if (u32SlotBit != 0U && ((s_uds_cleared_slots & u32SlotBit) == 0U)) {
    /* 必须显式写 magic：旧记录可能是擦除态(0xFFFFFFFF)，
     * 若 magic 无效，复位后 APP 的 App_CheckPendingUdsAck
     * 会因 magic 不匹配直接返回，导致 0x51/0x71 补发失败。 */
    state.magic = UDS_SHARED_MAGIC;
    state.phase = UDS_PHASE_PROGRAMMING_DONE;
    state.result = 1;
    state.target_slot = eSlot;
    UdsShared_Write(&state);
    ...
}
```

### 提交

- `715645b` fix(boot): force UDS_SHARED_MAGIC on OTA completion so APP can re-send 0x51/0x71 after reset

### 验证

1. 重新编译并烧录 boot；
2. 复现“双坏等待 UDS → 只烧 APP1 → TBOX 发 `0x11 01`”；
3. 预期：
   - boot RTT 不再出现 `WARNING: magic mismatch`；
   - APP1 启动后 RTT 打印 `Sending pending 11 01 ACK (51 01)`；
   - 总线上出现 `18DAF103  04 51 01 00 00 00 00 00`；
   - TBOX 收到 51 后不再 6 秒超时重试。
